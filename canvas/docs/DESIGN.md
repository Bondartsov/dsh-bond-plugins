# Холст — как устроено

Плагин `@local/dsh-canvas` состоит из двух половин: Host (`index.js` + `lib/`) и клиент
(`client.js`). Обе половины ходят в **один** сервис `CanvasService`: и инструменты модели, и
маршруты панели вызывают его методы, поэтому «дописать абзац» имеет ровно одно определение.

```
ассистент ──tools──┐
                   ├── CanvasService ── CanvasStore ── <профиль>/canvas/*.json
панель ───routes───┘        │
                            ├── markdown.js   разбор markdown-lite
                            ├── anchors.js    перепривязка комментариев
                            ├── edits.js      коммит: порядок, конфликты, хеши
                            ├── style.js      стилевой паспорт и дрейф
                            └── export-html.js автономная страница
```

## Язык

Плагин русскоязычный на 100 % в той части, которую читает человек:

- подписи, кнопки, состояния, подсказки, баннеры и ошибки панели — русские;
- результаты инструментов (то, что видно в беседе как ответ инструмента) — русские;
- подсказки в ошибках `<CODE>: <hint>` — русские, код остаётся латиницей как идентификатор
  протокола;
- экспортируемый HTML — `lang="ru"`, все подписи русские;
- `locale/` содержит только `ru.json`, английского словаря нет. Клиент берёт формулировки из
  встроенного русского словаря и не зависит от языка интерфейса: если сборка ответит `en` или
  вернёт сам ключ, на экране всё равно будет русский текст.

Английскими осознанно остаются только **описания инструментов модели** (`description` и схемы
параметров): по спецификации F3 они пишутся на английском в коде и не локализуются. Секция
системного промпта — по-русски, как и весь остальной текст плагина.

## Модель данных

Документ — упорядоченный список **блоков**; блок — закрытый тип и rich text в виде spans.

```json
{
  "schema": 1,
  "id": "doc-1",
  "scope": "global",
  "sessionId": null,
  "title": "Коммерческое предложение",
  "version": 12,
  "nextBlockSeq": 7,
  "nextCommentSeq": 3,
  "blocks": [{ "id": "b-2", "type": "p", "spans": [{ "t": "Уважаемый Иван Иванович, " }, { "t": "переносим", "i": true }] }],
  "comments": [{ "id": "c-1", "blockId": "b-2", "from": 0, "to": 32, "occurrence": 0, "quote": "…", "note": "…", "status": "open", "reason": null, "createdAt": "2026-11-06T13:18:04+03:00" }],
  "style": { "tone": "деловой", "person": "вы", "avgSentence": 14, "flags": ["канцелярит"] },
  "updatedAt": "2026-11-06T13:20:00+03:00"
}
```

### Почему блоки, а не один rich-text

1. **Якорь комментария — это пара чисел.** `from`/`to` считаются по «плоскому» тексту блока
   (конкатенация `t` всех spans). Пока границы блока не двигаются, офсет остаётся верным, и
   проверка «правка не вышла за диапазон» — арифметика, а не разбор дерева.
2. **Правка одного абзаца не переписывает остальные.** Коммит применяет замену внутри блока и
   сверяет SHA-256 всех остальных блоков; расхождение — ошибка планировщика, коммит отменяется.
3. **Ручная правка — это правка одного блока.** `contenteditable` стоит на блоке, а не на всём
   документе, поэтому браузер не перестраивает соседние абзацы и каретка не прыгает.
4. **Виртуализация и окно чтения.** `canvas_read` отдаёт окно по индексам блоков, а не 200 000
   знаков целиком.

Типы блоков закрыты: `h1 | h2 | h3 | p | li | quote | code` (`li` несёт `ordered`). Rich text —
только `{t, b?, i?}`: ни ссылок, ни цветов, ни размеров, поэтому документ нельзя «сломать»
разметкой, которую редактор не умеет показать.

### Идентификаторы

`b-<seq>` и `c-<seq>` выдаются из монотонных `nextBlockSeq` / `nextCommentSeq` документа. UUID не
используются: идентификатор должен быть коротким и читаемым в пакете модели. Счётчик не
уменьшается при удалении, поэтому коллизий после удаления не бывает.

### Версия

`version` растёт при **любом** изменении документа: текст, заголовок, комментарий, статус,
применение. Она же — значение `If-Match` для ручной правки. Сравнение идёт по целому числу:
заголовок `12` и `"12"` — одно и то же (`parseIfMatch`).

## Spans и плоские офсеты

```
spans: [ {t:"Уважаемый Иван Иванович, "}, {t:"переносим", i:true}, {t:" встречу..."} ]
плоский текст:  Уважаемый Иван Иванович, переносим встречу...
               ^ from=0                      ^ from=27     ^ to=36
```

Все офсеты — в плоском тексте. Рендер в HTML и обратная сериализация не меняют текст:

- `spansToHtml(spans, marks)` экранирует текст, оборачивает `b` в `<strong>`, `i` в `<em>`, а
  прокомментированные диапазоны — в `<mark data-comment>`;
- `serializeSpans(element)` читает DOM обратно: текст — как есть, `<strong>/<b>` — `b`,
  `<em>/<i>` — `i`, `<br>` — `\n`, `<mark>` — прозрачен.

Поэтому подсветка комментариев — украшение, а не часть текста: сериализация её игнорирует.

## Контракты инструментов

Ошибка инструмента всегда `<CODE>: <hint>`. Закрытый список кодов:
`CANVAS_FULL`, `INVALID_TEXT`, `UNKNOWN_BLOCK`, `UNKNOWN_COMMENT`, `NOTHING_TO_APPLY`,
`PENDING_MISSING`, `APPLY_IN_PROGRESS`, `EDIT_TOO_LONG`, `QUOTE_TOO_LONG`, `STALE_VERSION`,
`NO_SESSION` (+ маршрутные `UNKNOWN_DOC`, `UNKNOWN_BATCH`).

| Инструмент | Что делает | Отказы |
|---|---|---|
| `canvas_write {text, after?}` | дописывает блоки в конец или после `after` (blockId) | `EDIT_TOO_LONG` > 20 000, `CANVAS_FULL`, `UNKNOWN_BLOCK`, `INVALID_TEXT` |
| `canvas_replace {text}` | переписывает документ; **все** комментарии → `orphaned`, `reason: "документ перезаписан"` | `CANVAS_FULL`, `INVALID_TEXT` |
| `canvas_set_title {title}` | заголовок | `INVALID_TEXT`, `EDIT_TOO_LONG` |
| `canvas_clear {confirm:true}` | очищает блоки и комментарии, пишет историю | без `confirm` — `INVALID_TEXT` |
| `canvas_read {from?, to?, includeComments?}` | окно блоков, по умолчанию 30, максимум 100 | — |
| `canvas_comments {status?}` | список комментариев | `INVALID_TEXT` на неизвестный статус |
| `canvas_apply {commentIds?}` | готовит пакеты, один лок на документ | `NOTHING_TO_APPLY`, `APPLY_IN_PROGRESS` |
| `canvas_apply_edits {edits}` | принимает правки в pending-набор | `PENDING_MISSING`, `UNKNOWN_COMMENT`, `EDIT_TOO_LONG` |

Markdown-lite: `# `/`## `/`### ` → `h1/h2/h3`; `- ` → `li(ordered:false)`; `1. ` → `li(ordered:true)`;
`> ` → `quote`; ```` ``` ```` → `code`; `**b**`/`*i*` → spans. Пустая строка разделяет абзацы;
смена маркера тоже начинает новый блок.

## Маршруты панели

| Маршрут | Ответ |
|---|---|
| `GET /canvas/doc` | `{ version, document, readOnly, newerSchema }` |
| `PUT /canvas/doc` (`If-Match`) | `{ version, comments }`; `409 STALE_VERSION` |
| `POST /canvas/doc/new` | `{ version, document }` |
| `POST /canvas/comment` | `{ comment, version }`; `action: add/update/delete/resolve/reanchor` |
| `POST /canvas/apply/prepare {sessionId}` | `{ batchId, count }`; без `sessionId` → `400 NO_SESSION` |
| `GET /canvas/apply/pending` | `{ batchId, count, items[] }` или `204` |
| `POST /canvas/apply/commit {batchId, accept[]}` | `{ version, applied, conflicts }` |
| `POST /canvas/apply/discard {batchId}` | `{ restored, version? }` |
| `POST /canvas/export {format, includeComments}` | `{ path, bytes }` |

Статусы: `409` — `STALE_VERSION` / `APPLY_IN_PROGRESS`; `404` — `UNKNOWN_DOC` / `UNKNOWN_BATCH`;
`400` — валидация и `NO_SESSION`; `413` — превышение лимитов. Тело ошибки единое: `{ code, hint }`.

## Handshake применения

```
панель            Host                         модель
  │  POST prepare {sessionId}                   │
  │ ───────────────▶                            │
  │                один batch, packages, стиль   │
  │                agent.inject(контекст)        │
  │                agent.followup(инструкция) ──▶│  (пробуждение, без user-сообщения)
  │                                             │  canvas_apply {}
  │                packages + instruction ◀─────│
  │                                             │  canvas_apply_edits {edits}
  │                pending-набор ◀──────────────│
  │  GET pending (опрос)                        │
  │ ◀──────────────                             │
  │  человек отмечает галочки                   │
  │  POST commit {batchId, accept}              │
  │ ───────────────▶ атомарная запись            │
```

- **Один лок на документ.** `prepare` и модельный `canvas_apply` не идут одновременно:
  второй получает `APPLY_IN_PROGRESS`. Модельный `canvas_apply` во время UI-подготовки
  **присоединяется** к ней (иначе UI-путь был бы невозможен), но только один раз.
- **Модель не пишет в документ.** `canvas_apply_edits` складывает pending-набор; запись делает
  только коммит человека.
- **TTL 10 минут.** Истёк — все комментарии набора получают `failed` с `reason: "модель не
  ответила"`, pending очищается.
- **Частичный набор.** Правки не для всех комментариев: полученные применяются, остальные
  получают `failed` с причиной.
- **Идемпотентность.** Повторный коммит того же `batchId` возвращает сохранённый результат.
- **Атомарность.** Документ пишется во временный файл и переименовывается; ошибка записи
  оставляет и память, и файл прежними.
- **Отмена.** `discard` после коммита возвращает снимок «до коммита» — байт в байт — и снова
  открывает комментарии.

### Почему `inject` + `followup`

Проверено по сборке 0.2.2-rc.1 (`dsh-agent-loop`): `inject` кладёт сообщение в `next-step` и **не
будит** драйвер, `followup` кладёт в `next-turn` и **будит**. `followup()` без аргумента невозможен
— `send` обращается к `message.id`. Поэтому Host отправляет два сообщения: контекст (список
комментариев) через `inject` и короткую инструкцию через `followup`.

Оба несут `source.kind = "canvas"` — **собственный вид производителя**. Формат журнала сессии v4
(`dsh-session-format-v3-to-v4`, `source()`) прямо отвергает устаревшую обёртку
`kind: "plugin"`: сообщение с ней валит весь ход ошибкой
`format v4 message requires a producer-owned source kind`. С видом `canvas` строка становится
обычной контекстной вставкой: чат её не рисует как сообщение пользователя, а модель читает.

Если беседа открыта, но её агент не живой (свежий старт Host, сессия ещё не делала хода), Host
сначала пробует `agents.resume({ sessionId })` и только потом отвечает `NO_SESSION`: панель уже
смотрит в эту беседу, и «откройте её и повторите» было бы тупиком.

## Порядок правок и конфликты

1. Правки группируются по блоку и сортируются **по убыванию `to`** — правка правее не сдвигает
   офсеты левой.
2. Пересечение диапазонов в одном блоке: вторая (в порядке применения) получает
   `conflict: "пересекается с другой правкой этого блока"`.
3. `replacement` проверяется на: пустоту, равенство цитате, предел
   `min(max(3·|quote|, 50), 5000)`, выход за `[from, to)` (в правке оказался текст блока за
   границами), дрейф стиля.
4. После применения — перепривязка **остальных** комментариев блока, чтобы соседняя правка не
   осиротела.
5. Все нетронутые блоки сверяются по SHA-256; расхождение отменяет коммит.

## Перепривязка якорей

После любой правки блока каждый его комментарий проходит четыре шага:

1. точный поиск `quote` с учётом `occurrence` (если двойник исчез, берётся ближайшее вхождение, а
   `occurrence` исправляется);
2. нормализованный поиск: регистр, `ё`, пробельные серии;
3. ≥ 70 % слов цитаты в окне той же длины → `approximate` (бледная подсветка, правка применяется);
4. иначе → `orphaned` с `reason: "фрагмент не найден в блоке"`.

Осиротевший комментарий **не удаляется**: он остаётся в рейле с исходной цитатой и кнопкой
«Перепривязать». Ручная перепривязка пересчитывает `occurrence` и возвращает статус `open`, факт
пишется в историю.

## Стилевой паспорт и дрейф

`stylePassport(document)` детерминированно считает:

- `tone`: `деловой` при канцелярите, `разговорный` при коротких фразах и разговорных маркерах,
  иначе `нейтральный`;
- `person`: `вы` или `ты` по местоимениям и притяжательным;
- `avgSentence`: слова / предложения;
- `flags`: `канцелярит`, `длинные предложения`, `эмодзи`.

Паспорт пересчитывается на каждом `prepare` и попадает в документ вместе с коммитом (а не в
подготовку), чтобы отмена применения возвращала файл байт в байт.

Дрейф — два правила: новое эмодзи, которого в документе не было, и рост фрагмента больше чем в
2,5 раза. Сработало → `conflict` с `reason: "дрейф стиля"`.

## Клиент

- **Вкладка** `sidebarRightTabs.register({ id, kind, title, keepMounted: true })`; тело и заголовок
  — в keyed-слоты `sidebar.right.pane.tab` / `.title` под тем же `id`.
- **Кнопка** `canvas-open`, order 50, в `conversation.session.header.utilities`; бейдж показывает
  готовые правки, не открывая вкладку насильно.
- **Деградация**: если в сборке нет `sidebarRightTabs`, панель регистрируется страницей в `main`
  (key `canvas`) и пунктом в `sidebar.panellist`; каждая регистрация в своём `try/catch`.
- **Поллинг** `GET /canvas/doc`: 500 мс, пока последняя запись моложе 10 с, иначе 3 с. Скрытая
  вкладка не опрашивает документ; ответ с `version ≤` локальной игнорируется.
- **Typewriter**: `min(20 мс, 2500 / N)` на символ, без нижней границы; при `N > 1200` — сразу.
  Панель всегда рисует префикс новейшего текста, поэтому два обновления подряд не теряют символов.
- **Ручная правка**: `contenteditable` на блоке, сохранение по blur и по паузе 400 мс, `If-Match`.
- **Таймеры**: все создаются внутри `useEffect` и снимаются в его очистке; после размонтирования
  вкладки не остаётся ни одного таймера (сторож-тест 24).

## Хранение

`<профиль>/canvas/<id>.json` — документ, `<id>.history.json` — последние 20 операций,
`index.json` — активный документ. Запись атомарна (temp + rename) и синхронна там, где важна
целостность (коммит, очистка, отмена). Обычная правка дебаунсится 400 мс и досохраняется при
выгрузке плагина.

## Осознанные отклонения и умолчания

- **`canvas_clear` без `confirm` и 500-й комментарий** отказывают кодом `INVALID_TEXT`: в закрытом
  списке кодов нет отдельного «нужно подтверждение». Подсказка объясняет, что делать.
- **Документ со `schema > 1`** показывается только для чтения, а запись отклоняется
  `STALE_VERSION` с подсказкой «создан более новой версией DSH» — ближайший по смыслу код из
  списка.
- **`followup()` без аргумента** невозможен в этой сборке, поэтому пара `inject` + `followup` несёт
  два сообщения (см. выше).
- **Кнопка «PDF»** не открывает файл из браузера (у страницы нет доступа к файловой системе):
  она экспортирует HTML и показывает путь с подсказкой про печать.
- **`sidebar.panellist` + `main`** — проверенный по сборке набор слотов, но публичного способа
  переключить страницу из плагина в этой сборке нет; деградация регистрирует обе поверхности и
  открывает через `layout.selectPanel`, если сервис доступен. Основной путь — вкладка правого дока.
